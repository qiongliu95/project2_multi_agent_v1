# 项目二核心主线：需求到测试设计的 AI 工作流

## 1. 项目定位

本项目是一个面向“需求分析 → 风险识别 → 测试设计 → 汇总复核”流程的 AI Workflow Demo。

项目重点不是证明“多 Agent 一定优于单 Prompt”，而是将测试工作中真实存在的前置分析流程结构化，并验证在需求信息不完整的情况下，如何通过分阶段职责拆分与生成约束，让模型输出更可控、更可复核。

换句话说，本项目关注的不是“让模型生成更多内容”，而是：

* 如何避免模型在需求不完整时自动补全；
* 如何显式暴露需求缺口；
* 如何限制风险识别阶段的泛化；
* 如何防止测试设计阶段生成伪完整用例；
* 如何避免汇总阶段新增未确认信息；
* 如何保留人工复核入口。

---

## 2. 项目背景

在真实测试工作中，测试人员通常不会直接从一段需求描述进入测试用例编写。

更常见的流程是：

1. 先理解需求目标、用户角色、核心动作和业务边界；
2. 再识别需求中的缺失信息、歧义和待确认问题；
3. 然后判断可能的风险、异常流程和边界场景；
4. 在已知信息范围内设计测试点和用例草案；
5. 最后汇总关键风险和待确认项，交由产品、研发或测试负责人复核。

因此，“需求到测试设计”本质上是一个多阶段工作流，而不是一次性生成任务。

本项目正是基于这一测试工作流，将其拆解为多个 Agent 阶段，用 AI 承接不同环节的分析职责。

---

## 3. 核心问题

在实验过程中发现，如果让模型直接根据需求文本生成测试设计结果，容易出现以下问题：

### 3.1 常识补全

模型会在需求没有明确说明时，自动补充验证码、密码、邮箱、页面按钮、输入规则等内容。

这些内容看似合理，但并未来自原始需求，容易掩盖真实信息缺口。

### 3.2 风险泛化

模型容易生成通用 checklist，例如权限风险、性能风险、并发风险等。

如果这些风险与当前需求缺乏直接关系，输出就会变成泛化风险列表，而不是针对当前需求的分析结果。

### 3.3 伪完整测试

在信息明显不足的情况下，模型仍会生成完整测试用例、详细步骤和验收标准。

这类输出表面完整，但建立在未确认信息之上，容易误导后续使用者。

### 3.4 汇总扩写

汇总阶段容易在总结时新增问题、扩展风险，导致前面已经收敛的边界再次被放大。

---

## 4. 设计思路

项目采用“需求解析 → 风险识别 → 测试设计 → 汇总复核”的多阶段 Agent Workflow。

每个 Agent 对应真实测试工作中的一个阶段：

| 测试工作阶段 | Agent 设计    | 核心职责                          |
| ------ | ----------- | ----------------------------- |
| 需求理解   | Agent1：需求解析 | 抽取需求目标、用户角色、核心动作、边界条件和待澄清问题   |
| 风险判断   | Agent2：风险识别 | 基于需求和待澄清问题识别歧义、缺失、异常流和数据/状态风险 |
| 测试设计   | Agent3：测试设计 | 在已知信息范围内生成测试点、异常测试点、验收标准和用例草案 |
| 汇总复核   | Agent4：结果汇总 | 汇总上游结果，输出关键待确认项和人工复核建议        |

这种拆分不是为了堆叠 Agent 数量，而是为了让测试工作流中的不同职责具备清晰边界，并对每一层施加不同的生成约束。

---

## 5. 分阶段生成约束

项目的核心不是多 Agent 本身，而是每一层的生成约束。

### 5.1 Agent1：需求解析约束

Agent1 只负责从原始需求中提取已知信息，不允许进行常识补全。

当需求中缺少流程、规则、条件、页面或异常处理信息时，不允许自行补充，而是统一进入 open_questions。

目标是让信息缺口显性化。

### 5.2 Agent2：风险识别约束

Agent2 的风险来源必须限制在：

* 原始需求文本；
* Agent1 输出的已知信息；
* Agent1 暴露的 open_questions。

禁止生成与当前需求无直接关系的通用 checklist 风险。

目标是让风险识别保持与当前需求相关，而不是变成泛化风险枚举。

### 5.3 Agent3：测试设计约束

Agent3 只能基于已知信息生成测试点和测试草案。

当关键信息不足时，不允许生成完整测试用例，而是输出 test_case_drafts，并保留待确认项。

目标是避免“看似完整、实际建立在假设上”的伪完整测试结果。

### 5.4 Agent4：汇总约束

Agent4 只允许汇总上游已有结果，不允许新增问题、扩展风险或引入新的业务假设。

目标是避免汇总阶段重新扩大边界，保证最终结果可追溯、可复核。

---

## 6. 当前项目价值

本项目当前已经完成的核心价值是：

1. 将测试设计前置流程结构化为可复用 AI Workflow；
2. 识别出需求到测试设计场景中常见的 LLM 失控模式；
3. 通过分阶段职责边界限制模型补全、泛化和伪完整生成；
4. 将“直接生成完整用例”调整为“暴露缺口 + 输出测试草案”；
5. 保留人工复核入口，避免 AI 输出直接进入下游执行环节。

因此，本项目更准确的定位是：

一个围绕测试工作流的 AI 输出约束实验。

---

## 7. 当前边界

当前版本主要基于单段需求文本输入，适合验证：

* 需求信息是否被正确提取；
* 信息缺口是否被暴露；
* 模型是否发生常识补全；
* 风险识别是否泛化；
* 测试设计是否生成伪完整用例；
* 汇总阶段是否新增信息。

当前版本不定位为完整测试用例自动生成系统。

因为真实测试设计质量高度依赖项目背景、业务规则、页面信息、系统上下文、历史缺陷和行业约束。

当前版本更适合作为：

* 测试工作流 AI 化原型；
* 生成约束机制验证 Demo；
* 测试经验迁移到 AI 产品设计的展示项目。

---

## 8. 后续增强方向

后续如果要提升真实业务场景下的准确性，优先方向不是继续增加 Agent 数量，而是补充上下文层和评测基线。

### 8.1 Expected Behavior Baseline

为不同类型需求建立期望行为基线，用于判断：

* 哪些动作必须识别；
* 哪些信息缺口必须暴露；
* 哪些内容禁止模型补全；
* 哪些风险可以进入测试设计；
* 哪些输出只能作为人工参考；
* 信息不足时是否应该停止生成完整用例。

### 8.2 Context Layer

引入项目背景、业务规则、页面信息、系统上下文、行业背景等内容，提高测试设计的真实可用性。

当前版本的主要目标是控制错误生成；Context Layer 才是后续提高准确性的关键。

---

## 9. 一句话总结

本项目不是为了证明多 Agent 一定优于单 Prompt，而是将真实测试工作中的“需求分析、风险识别、测试设计、汇总复核”流程结构化为 AI Workflow，并通过分阶段生成约束，让模型在信息不足时暴露缺口、停止伪完整生成，输出更可控、更可复核的测试设计草案。
