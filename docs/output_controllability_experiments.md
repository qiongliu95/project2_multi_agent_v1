# Output Controllability Experiments
# 输出可控性实验

## 1. 文档定位

本文档用于记录项目二在多 Agent 工作流实验过程中形成的输出可控性设计方法。

本项目不是完整的多智能体平台，也不是 Prompt 工程项目，而是一个面向“需求分析与测试设计”场景的可控生成实验。

项目重点验证：

- 多 Agent 拆分是否能够提升输出可控性与稳定性
- 模型在信息不足时是否会自动补全需求
- 系统是否可以在信息不足时停止生成，而不是强行输出完整结果
- 当 Prompt 优化收益下降时，是否需要转向 Schema、结构或流程层调整

本文档关注的核心问题不是：

> Prompt 如何持续优化

而是：

> 系统如何通过多层控制机制提升输出可控性。

---

## 2. 市场视角下的项目价值

当前 AI 产品经理岗位并不只要求会写 Prompt，更强调：

- 能理解 LLM / Agent / RAG / 工作流编排等 AI 应用层能力
- 能围绕具体业务场景进行 Badcase 分析与效果评估
- 能设计模型输出的质量控制机制
- 能判断哪些问题可以通过 Prompt 改善，哪些问题需要通过产品结构、评估机制或人工流程解决
- 能将 AI 能力落到具体产品链路，而不是停留在模型能力展示

因此，项目二的价值不应表述为：

> 我做了一个多 Agent 流程，并优化了 Prompt。

而应表述为：

> 我围绕需求分析与测试设计场景，验证了多 Agent 工作流的输出可控性边界，并通过 Badcase 收敛、Schema 重构、任务拆分和停止规则，形成了一套可复核的输出控制方法。

---

## 3. 项目主线

项目二构建了一套“需求 → 风险 → 测试 → 汇总”的多 Agent 串行工作流。

基础链路为：

```text
需求输入
↓
Agent1：需求解析
↓
Agent2：风险识别
↓
Agent3：测试设计
↓
Agent4：结果汇总
```

项目初始目标是验证：

- 多 Agent 拆分是否比单 Agent 更稳定
- 每个 Agent 是否可以承担更单一的职责
- 结构化输出是否更便于复核

但实验过程中发现：

> 多 Agent 拆分本身不能保证稳定性。

即使拆分为多个 Agent，系统仍然会出现：

- Agent1 自动补全需求
- Agent2 风险泛化
- Agent3 生成伪完整测试用例
- Agent4 汇总阶段扩写

因此，项目主线从：

> 如何让 AI 生成需求分析与测试设计结果

逐步转向：

> 如何让 AI 在边界内生成可复核结果。

---

## 4. AI 天然修补风格 vs 项目最终形成风格

在实验过程中，AI 协作本身也暴露出一种典型倾向：

> 发现问题后，优先在现有结构内补规则、补 Prompt、补禁止项。

如果完全沿着这种方式推进，项目容易演变为：

```text
发现问题
↓
补 Prompt
↓
出现新问题
↓
继续补 Prompt
↓
Prompt 越来越长
↓
规则越来越多
↓
系统越来越难维护
```

这种方式可以解决部分局部问题，但容易产生：

- 规则堆叠
- 规则冲突
- 局部优化导致全局退化
- Prompt 难以维护
- 问题反复迁移

项目最终形成的风格不是持续补规则，而是：

```text
发现问题
↓
判断问题属于哪一层
↓
Prompt 层能解决则收敛 Prompt
↓
Prompt 层解决不了则调整 Schema
↓
Schema 仍不足则拆分任务结构
↓
持续优化收益下降则停止修改
```

因此，项目最终形成的是一种分层归因式的输出可控性设计。

| 对比项 | AI 天然修补风格 | 项目最终形成风格 |
|---|---|---|
| 问题处理 | 发现问题就补规则 | 先判断问题在哪一层 |
| Prompt | 持续增加禁止项 | 约束分类与结构化 |
| 输出 | 追求完整生成 | 允许停止生成 |
| Schema | 默认沿用字段 | 重新定义输出对象 |
| 架构 | 在现有管道内修补 | 必要时拆分混合任务 |
| 迭代 | 持续优化 | 引入停止规则 |
| 价值 | 局部修复 | 全局可控性 |

## 5. 失控模式分析

### 5.1 Implicit Completion：隐式补全

#### 表现

Agent1 在需求解析阶段自动补充原需求中未出现的信息。

例如在手机号注册场景中，模型容易自动补充：

- 验证码
- 密码
- 邮箱
- 登录凭证

#### 原因

模型会根据训练数据中的常见业务流程自动补齐缺失信息。

对于“手机号注册”这类需求，模型容易默认关联完整注册链路，而不是严格停留在原始需求文本。

#### 影响

- 引入需求中不存在的信息
- 掩盖真实信息缺口
- 导致下游 Agent 基于错误信息继续推理
- 使系统输出看似完整，但实际越界

---

### 5.2 Checklist Expansion：风险泛化

#### 表现

Agent2 在风险识别阶段输出大量通用风险，而不是当前需求真实暴露出的风险。

典型表现包括：

- 权限风险泛化
- 数据风险泛化
- 性能风险泛化
- 安全风险泛化
- 输出逐渐接近通用 Checklist

#### 原因

风险识别任务天然容易诱导模型追求覆盖率。

模型会倾向于输出“可能有帮助的风险列表”，而不是严格判断“当前需求文本中真实暴露出的风险”。

#### 影响

- 风险数量增加
- 风险与需求关联度下降
- 下游测试设计被无关风险干扰
- 人工复核成本上升

---

### 5.3 False Completeness：伪完整生成

#### 表现

Agent3 在信息不足时仍然生成完整测试用例。

典型表现包括：

- 缺少业务规则仍输出完整测试步骤
- 缺少异常处理规则仍输出完整预期结果
- 缺少验收标准仍生成完整测试用例

#### 原因

模型倾向于完成任务，而不是指出任务无法完成。

当 Prompt 要求“生成测试用例”时，即使信息不足，模型也会使用推断内容补齐结果。

#### 影响

- 输出看似完整
- 实际缺少依据
- 容易误导使用者认为需求已经足够清晰
- 掩盖需要人工确认的缺口

---

### 5.4 Summary Drift：汇总漂移

#### 表现

Agent4 在汇总阶段新增问题、新增风险或新增解释。

典型表现包括：

- 将 Agent2 的抽象风险改写成新的 critical_open_questions
- 在 Agent1 未提出的问题基础上新增问题维度
- 将汇总任务扩展为补充建议任务

#### 原因

模型默认将“汇总”理解为：

```text
总结 + 提炼 + 补充建议
```

但在本项目中，Agent4 的职责应是汇总已有结果，而不是再次创造内容。

#### 影响

- 汇总结果大于输入结果
- 破坏结果可追溯性
- 重新引入扩写风险
- 使最终输出边界不清晰

---

## 6. 控制机制设计

项目最终发现：

> 稳定性来自控制机制，而不是 Agent 数量。

控制机制不是单层 Prompt，而是由 Prompt、Schema、Architecture、Process 四层共同组成。

---

### 6.1 Prompt Layer：行为边界控制

#### 目标

约束模型在当前任务中的行为边界。

#### 典型机制

- 信息来源约束
- 风险来源约束
- 汇总边界约束
- 禁止举例表达
- 禁止候选项列举
- 禁止补充原文未出现的业务机制

#### 解决的问题

- 自动补全
- 风险泛化
- 汇总扩写

#### 约束结构化

早期 Prompt 中，多个约束类型混合在一起：

- 信息来源约束
- 行为约束
- 推理约束
- 输出规则
- 字段说明

随着问题增多，单纯增加规则会导致：

- Prompt 越来越长
- 修改成本增加
- 规则之间关系不清晰
- 问题定位困难
- 规则冲突风险上升

因此，后续需要对 Prompt 约束进行结构化组织：

```text
Information Source Constraints
Reasoning Constraints
Behavior Constraints
Output Rules
```

约束结构化的目的不是增加规则数量，而是提升约束的可维护性、可解释性和问题定位能力。

---

### 6.2 Schema Layer：输出定义控制

#### 目标

约束系统输出对象的语义，避免字段定义本身诱导模型越界。

#### 典型案例一：test_cases → test_case_drafts

早期 Agent3 使用 `test_cases` 字段。

问题在于：

```text
信息不足
↓
仍要求输出完整 test_cases
```

这会诱导模型生成伪完整测试用例。

因此后续将字段调整为：

```text
test_case_drafts
```

该字段表达的是“测试用例草案”，而不是完整测试用例。

这使系统可以在信息不足时输出：

- 可参考的测试方向
- 待补充的测试草案
- 需要人工确认的缺口

而不是强行生成完整结果。

#### 典型案例二：critical_open_questions 来源限制

Agent4 早期会将风险扩写为新的关键问题。

后续约束为：

```text
critical_open_questions 只能复用已有 open_questions
```

该调整不是简单 Prompt 规则，而是对汇总结果字段来源的定义约束。

#### 解决的问题

- 伪完整输出
- 字段语义混乱
- 汇总扩写
- 结果不可追溯

---

### 6.3 Architecture Layer：任务结构控制

#### 目标

当单一 Agent 内部混合多个认知任务时，通过拆分任务结构提升稳定性。

#### 典型案例：Agent1 三阶段结构

Agent1 的 `open_questions` 生成长期不稳定。

早期尝试持续优化 Prompt，但问题仍然反复出现：

- 有时漏掉关键问题
- 有时过度追问
- 有时引入设计选项
- 有时将流程问题拆得过细

后续分析发现，`open_questions` 实际混合了三个动作：

1. 识别需求中的动作
2. 判断每个动作是否存在信息缺口
3. 选择哪些缺口需要形成问题

因此引入结构拆分：

```text
Parsing
↓
Gap Detection
↓
Selection
```

并增加中间状态：

```text
action_gap_candidates
```

用于显式标记每个 action 的信息缺口。

#### 解决的问题

- open_questions 不稳定
- 缺口识别不可观测
- 问题生成过度依赖一次性判断
- 复杂需求下随机波动

#### 关键结论

Three-Stage 不是为了增加系统复杂度，而是在多轮 Prompt 优化仍不稳定后，对混合任务进行拆解得到的结果。

---

### 6.4 Process Layer：优化过程控制

#### 目标

约束优化行为本身，避免陷入无止境 Prompt 调优。

#### 问题来源

实验后期发现：

```text
发现问题
↓
修改 Prompt
↓
局部问题改善
↓
下游 Agent 出现新问题
↓
继续修改
↓
系统震荡
```

即：

> 局部优化不一定带来全局稳定。

#### Prompt Stop Rule

当同一个 Agent 围绕同一类问题连续修改多次，且仍未稳定时，停止继续微调 Prompt，转入结构或扩展方案设计。

#### 判断标准

继续修改前，需要判断：

- 该问题是否属于 Prompt 层问题
- 是否属于 Schema 定义问题
- 是否属于任务结构问题
- 是否只在单个 Case 中出现
- 修改收益是否大于副作用
- 是否已经达到当前版本展示目标

#### 解决的问题

- 无止境 Prompt 调优
- 规则持续堆叠
- 修复一个问题引入另一个问题
- baseline 稳定性被破坏

---

## 7. 系统边界证据

本项目需要证明：

> 部分问题并非单纯 Prompt 能力不足，而是当前统一 Pipeline 与 LLM 生成机制共同造成的边界问题。

这需要用实验现象支撑，而不是主观判断。

---

### 7.1 证据一：同类问题跨 Case 重复出现

在不同需求类型中，类似问题反复出现。

例如：

- CRUD 类需求中出现过度追问和设计选项引入
- AI 能力类需求中出现流程子维度展开和常识补全
- 工具类需求中再次出现流程问题展开
- 能力型需求中出现 main_flow 提取不稳定

说明问题并非单一 Case 偶发错误，而是在不同需求类型下反复暴露。

---

### 7.2 证据二：同类失控模式跨 Agent 出现

不同 Agent 的失控表现不同，但底层倾向相似：

- Agent1 补足需求细节
- Agent2 补足风险清单
- Agent3 补足测试用例
- Agent4 补足总结建议

共同特征是：

> 模型倾向补足缺失信息，而不是停留在不完整状态。

这说明问题不是某一个 Agent 的孤立缺陷，而是 LLM 在结构化分析任务中的共同倾向。

---

### 7.3 证据三：局部优化影响全局稳定性

多 Agent 串行结构中，上游输出会影响下游 Agent。

例如：

```text
Agent1 open_questions 过度展开
↓
Agent2 承接这些问题并放大风险
↓
Agent3 基于风险生成测试点
↓
Agent4 汇总时进一步扩写
```

因此，修改单个 Agent 并不一定只影响该 Agent，而可能影响整个链路。

---

### 7.4 证据四：Prompt 优化存在收益递减

实验后期出现：

- 同类问题多轮修改后仍反复出现
- 修复一个 Case 后，换 Case 又回归
- 为某一场景增加规则后，其他场景表现受影响
- Prompt 复杂度不断提高，但稳定性提升有限

因此，项目最终停止继续堆叠 Prompt，而是将部分问题转入后续扩展方向。

---

## 8. 当前限制

当前版本已经实现了输出可控性提升，但并未完全解决所有问题。

---

### 8.1 轻微语义扩展无法完全消除

最终冻结版本中，仍然存在：

- Agent2 轻微语义扩展
- Agent4 偏总结型表达

项目结论不是：

> 扩展已经被完全消除。

而是：

> 扩展被压缩到可接受范围内。

---

### 8.2 统一 Pipeline 存在泛化边界

实验中已经识别到，不同需求类型关注点不同。

例如：

- CRUD 类关注数据状态、权限、异常操作
- 流程类关注角色、状态流转、审批路径
- AI 能力类关注输入范围、输出标准、结果评估
- 工具类关注输入处理、输出结果、失败恢复

当前版本使用统一 Pipeline 进行验证，能够暴露多类型需求下的稳定性问题，但并不是所有需求类型下的最优方案。

该问题不是当前版本“未考虑到”的缺陷，而是已识别但未在第一阶段继续展开的后续方向。

---

### 8.3 样本规模有限

当前项目使用的是小规模 Case 集，能够用于观察失控模式和验证收敛方向，但不能证明系统具备大规模泛化能力。

因此，不能将当前结果夸大为：

> 系统已适用于所有需求类型。

更准确的结论是：

> 当前实验验证了统一 Pipeline 下的可控性提升，并暴露了进一步分类处理的必要性。

---

### 8.4 尚未形成自动评估闭环

当前项目已有实验日志和 Case 输出记录，但自动化评估能力仍不足。

尚未完整实现：

- 自动计算字段完整率
- 自动检测越界扩写
- 自动对比不同版本输出稳定性
- 自动统计 Badcase 类型
- 自动判断一次修改是否提升整体质量

这也是后续需要补强的方向。

---

### 8.5 尚未产品化落地

当前项目定位为 Agent Demo，不是完整业务系统。

尚未实现：

- 多用户协同
- 权限体系
- 历史记录管理
- 工单系统集成
- 测试管理平台接入
- 企业级审批流
- 成本、延迟、并发评估

这符合当前项目边界，但在面向真实产品落地时需要补充。

---

## 9. 为什么停止继续优化

项目停止继续优化，并不是因为所有问题完全消失。

停止的原因是：

> 继续优化 Prompt 的边际收益下降，且可能破坏 baseline 稳定性。

典型表现包括：

- 问题反复出现
- Case 迁移后重新出现
- 修复一个问题引入另一个问题
- Prompt 复杂度持续增加
- 上游 Agent 修改影响下游输出

因此，项目最终选择冻结 baseline，并将后续改进放入 extension 机制中。

停止优化本身也是一种产品判断：

> 当前版本已经达到展示目标，继续追求局部最优不一定带来全局收益。

---

## 10. 后续优化方向

### 10.1 需求类型分类

后续可引入需求类型识别，将不同需求分为：

- CRUD 类
- 流程类
- AI 能力类
- 工具类
- 平台类

不同类型需求可以采用不同的解析策略、风险识别重点和测试设计模板。

目标不是增加复杂度，而是验证：

> 需求类型差异是否是影响统一 Pipeline 稳定性的主要变量。

---

### 10.2 差异化 Pipeline 或策略分支

当前版本使用统一 Pipeline。

后续可以探索：

```text
需求类型识别
↓
选择对应策略
↓
执行对应 Agent 流程
```

例如：

- CRUD 类强化数据状态与权限边界
- 流程类强化状态流转和角色关系
- AI 能力类强化输入输出标准与评估条件
- 工具类强化输入处理、结果返回和失败处理

---

### 10.3 自动评估机制

后续应建立更明确的评估指标，例如：

- 字段完整率
- 越界扩写率
- open_questions 有效率
- 风险关联度
- 测试点可执行性
- 汇总一致性
- 版本间稳定性

目标是判断：

> 一次修改是否真正提升整体稳定性，而不是只改善单个 Case。

---

### 10.4 人工决策支持

当前项目保留人工复核节点，但后续不能只停留在“让人审核”。

更合理的方向是：

> 为人工提供判断依据，降低确认成本。

例如，每个关键风险或待确认问题应尽量提供：

- 来源：来自原始需求、Agent1 open_questions 还是 Agent2 risk
- 原因：为什么该问题需要确认
- 影响：如果不确认，会影响哪些测试设计或验收标准

目标是：

```text
AI 输出候选结果
↓
系统提供依据
↓
人工快速确认
```

而不是：

```text
AI 输出大量内容
↓
人工重新分析一遍
```

---

### 10.5 Extension 机制继续保留

后续能力不应直接污染 baseline。

扩展模块应遵循：

- 默认关闭
- 不影响 baseline 可运行
- 失败时可绕过
- 仅在明确验证目标下启用

这种方式可以保证：

> baseline 稳定性优先，扩展能力独立验证。

---

## 11. 项目最终特色总结

项目二最终形成的特色不是：

> 做了一个多 Agent 流程。

也不是：

> 写了很多 Prompt 约束。

而是：

> 通过多轮 Badcase 收敛，识别了 LLM 在需求分析与测试设计任务中的失控模式，并通过 Prompt、Schema、Architecture、Process 四层控制机制，验证了多 Agent 输出可控性的形成过程与边界。

项目证明：

- 多 Agent 拆分在结构上有价值
- 但多 Agent 本身不能保证稳定性
- 稳定性来自每一层的控制机制
- Prompt 可以改善问题，但不能解决所有问题
- 当 Prompt 优化收益下降时，需要回到定义、结构和流程层重新归因
- 对于当前统一 Pipeline 无法完全解决的问题，应转入需求类型分类、自动评估和人工决策支持等后续方向

---

## 12. 面试表达建议

可以这样表达项目二：

> 这个项目不是为了证明我能做一个复杂 Agent 系统，而是为了验证多 Agent 在需求分析与测试设计场景中是否能提升输出可控性。  
> 最初我以为问题主要是 Prompt 不够强，但实验中发现，多 Agent 拆分后仍然会出现自动补全、风险泛化、伪完整生成和汇总扩写。  
> 后来我没有继续单纯堆 Prompt，而是把问题分层处理：Prompt 层限制信息来源，Schema 层把 test_cases 改为 test_case_drafts，Architecture 层把 Agent1 拆成 Parsing、Gap Detection、Selection，Process 层引入停止规则，避免无止境调 Prompt。  
> 所以项目最终的核心结论是：多 Agent 本身不能保证稳定性，稳定性来自 Prompt、Schema、Architecture、Process 多层控制机制。

---

## 13. 项目边界声明

当前项目适合作为 AI 产品经理作品集中的：

> Agent 工作流 + 输出可控性验证项目。

不应包装为：

- 完整 Agent 平台
- 企业级测试管理系统
- 大规模自动化评估系统
- 全场景需求分析产品

当前版本的合理定位是：

> 一个小型但可解释、可复核、可展示的 Agent Demo，用于说明如何从测试经验出发，设计 AI 输出质量控制机制。
