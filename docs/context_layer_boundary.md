# Context Layer Boundary

## 1. 文档目的

本文档用于说明项目《Requirement-to-Test Multi-Agent Workflow》中 Context Layer 的定位、价值与当前边界。

在项目复盘过程中发现，当前 Workflow 已经能够完成：

* 需求解析
* 风险识别
* 测试设计草案
* 结果汇总
* 信息缺口暴露
* 生成边界控制

但当前版本主要基于单段需求文本输入，缺少真实业务上下文。因此，它更适合验证“如何控制错误生成”，而不是直接生成高准确率的完整测试用例。

Context Layer 是后续提升真实业务准确性的关键增强方向，但不纳入当前版本实现范围。

---

## 2. 当前版本输入边界

当前版本输入主要是：

```text
单段需求文本
```

例如：

```text
用户可以通过手机号注册账号，注册后可以登录系统。
```

或：

```text
用户可以创建和删除自己的笔记。
```

这种输入能够支持系统识别：

* 当前需求中已经出现的角色；
* 当前需求中已经出现的动作；
* 当前需求中已经出现的对象；
* 当前需求中缺失的流程、规则、页面、状态和异常处理信息。

但无法充分支持系统判断：

* 当前功能属于什么业务系统；
* 该功能和已有功能有什么关系；
* 是否已有权限体系；
* 是否已有页面规范；
* 是否已有异常处理规则；
* 该行业是否有特殊约束；
* 历史缺陷中是否存在高风险模块；
* 当前需求是 0-1 新功能，还是成熟系统中的迭代需求。

因此，当前版本的输出更适合定位为：

```text
测试设计草案
+
待确认问题
+
风险提示
+
人工复核建议
```

而不是完整可执行测试用例。

---

## 3. 为什么 Context Layer 能提高准确性

测试设计质量高度依赖上下文。

同一个需求，在不同产品阶段、不同业务系统、不同用户角色和不同页面环境下，测试重点会明显不同。

例如：

```text
用户可以创建和删除自己的笔记。
```

如果它是一个 0-1 个人笔记产品，测试重点可能集中在：

* 创建流程；
* 删除流程；
* 数据保存；
* 页面交互；
* 删除后的状态。

但如果它是一个成熟协作平台中的新增能力，测试重点可能还需要关注：

* 权限边界；
* 多人协作；
* 历史版本；
* 同步状态；
* 审计记录；
* 数据恢复；
* 与已有模块的兼容性。

仅凭单段需求文本，模型无法可靠判断这些内容。

因此，如果要提高真实业务场景下的测试设计准确性，必须引入 Context Layer。

---

## 4. Context Layer 包含什么

Context Layer 可以包括以下信息：

## 4.1 项目背景

例如：

* 当前项目是什么类型；
* 面向什么用户；
* 处于什么阶段；
* 是新产品还是成熟产品迭代；
* 当前需求的业务目标是什么。

## 4.2 业务规则

例如：

* 角色权限规则；
* 状态流转规则；
* 数据处理规则；
* 审批规则；
* 异常处理规则；
* 业务限制条件。

## 4.3 系统上下文

例如：

* 已有功能模块；
* 当前功能与其他模块的关系；
* 上下游依赖；
* 数据来源；
* 数据去向；
* 已有系统约束。

## 4.4 页面与交互信息

例如：

* 页面入口；
* 页面结构；
* 操作按钮；
* 表单字段；
* 交互流程；
* 提示文案；
* 错误状态展示。

## 4.5 行业背景

例如：

* 电商场景；
* 安防场景；
* 内容审核场景；
* 企业管理场景；
* AI 能力场景；
* 数据报表场景。

不同场景下，对风险和测试重点的判断不同。

## 4.6 历史缺陷与风险信息

例如：

* 历史高频 bug；
* 曾经出问题的模块；
* 回归风险；
* 性能瓶颈；
* 易错业务规则；
* 用户投诉点。

---

## 5. 当前为什么不实现 Context Layer

当前版本不实现 Context Layer，主要基于以下原因。

## 5.1 当前项目目标不是完整产品化系统

当前项目重点是验证：

* 测试工作流是否可以被 AI Workflow 承接；
* 不同阶段是否可以施加生成约束；
* 信息不足时是否可以暴露缺口；
* 模型是否能够停止伪完整生成；
* 输出是否具备可复核性。

如果在当前阶段引入复杂上下文管理，会扩大项目边界。

---

## 5.2 Context Layer 会引入新的变量

一旦引入项目背景、行业背景和系统上下文，需要额外判断：

* 上下文来源是否可靠；
* 上下文是否完整；
* 上下文是否与当前需求相关；
* 上下文之间是否存在冲突；
* Agent 是否错误引用上下文；
* 上下文是否引入新的补全风险。

这会让项目从“生成约束验证”扩展为“上下文管理系统设计”。

这超出当前 MVP 范围。

---

## 5.3 当前评测集尚未完全成熟

在缺少 Expected Behavior Baseline 之前，直接引入 Context Layer 会导致另一个问题：

```text
无法判断输出提升到底来自上下文增强，
还是来自模型生成得更像真实业务。
```

因此，合理顺序应该是：

```text
先建立 Expected Behavior Baseline
↓
再引入 Context Layer
↓
最后验证上下文是否提升真实准确性
```

当前版本优先补齐评测基线，而不是直接实现上下文层。

---

## 6. 当前版本与 Context Layer 的关系

当前版本解决的是：

```text
在上下文不足时，如何避免错误生成。
```

Context Layer 解决的是：

```text
在补充业务上下文后，如何提高测试设计准确性。
```

两者关注点不同。

当前版本的重点是：

* 不乱补；
* 不泛化；
* 不伪完整；
* 暴露缺口；
* 保留人工复核。

Context Layer 的重点是：

* 更理解业务；
* 更贴近真实系统；
* 更准确判断风险；
* 更准确生成测试设计；
* 更接近实际可执行测试用例。

因此，Context Layer 是二期增强方向，而不是当前版本的必要实现。

---

## 7. 二期增强方向

如果后续继续扩展项目，可以将系统升级为：

```text
Context Layer
↓
Requirement Input
↓
Requirement Parsing
↓
Risk Analysis
↓
Test Design
↓
Result Summary
↓
Human Review
```

其中 Context Layer 可作为 Agent Workflow 的前置输入层，为后续 Agent 提供业务背景和系统约束。

二期可重点验证：

* 引入项目背景后，open_questions 是否更精准；
* 引入业务规则后，风险识别是否更贴近当前系统；
* 引入页面信息后，测试点是否更具可执行性；
* 引入历史缺陷后，风险识别是否更有针对性；
* 引入行业背景后，是否减少泛化风险；
* 上下文是否会引入新的错误补全。

---

## 8. 当前结论

当前版本不实现 Context Layer。

原因不是 Context Layer 不重要，而是当前项目阶段重点不同。

当前版本重点在于：

```text
测试工作流 AI 化
+
分阶段生成约束
+
信息缺口暴露
+
停止伪完整生成
```

Context Layer 属于后续提升真实业务准确性的增强方向。

因此，当前项目边界可以明确为：

```text
一期：验证在单段需求文本输入下，如何通过 AI Workflow 控制错误生成。
二期：引入项目背景、业务规则、页面信息和行业上下文，提高测试设计准确性。
```

---

## 9. One-Sentence Summary

Context Layer 是提升测试设计准确性的关键，但当前版本不实现该能力；当前项目优先验证测试工作流 AI 化与分阶段生成约束，Context Layer 作为二期增强方向，用于后续提升真实业务场景下的输出准确性。
