# 项目定义

## 项目名称

需求到测试设计的 Multi-Agent 工作流

一个面向需求分析与测试设计的 Multi-Agent 工作流，重点关注测试工作流建模、输出可控性、结构化推理与边界约束生成。

# 1. Background

在真实研发过程中，测试人员通常不会直接从一段需求描述进入测试用例编写。

更常见的流程是：

```text
需求理解
↓
信息缺口识别
↓
风险判断
↓
异常流程分析
↓
测试设计
↓
汇总复核
```

因此，“需求到测试设计”本质上不是一次性生成任务，而是一个多阶段分析流程。

随着大语言模型能力增强，AI 已经能够辅助完成：

* 需求分析
* 风险识别
* 测试设计
* 验收标准生成

但在实际使用过程中发现，如果让模型直接根据需求文本生成结果，容易出现：

* 自动补全缺失信息
* 风险泛化
* 伪完整结果
* 输出结构不稳定
* 信息来源不可追踪
* 汇总阶段扩写

这些问题会导致：

```text
结果看起来完整，
但实际可信度较低。
```

因此，本项目并不关注生成更多内容，而是关注：

> 如何将测试设计前置流程结构化为 AI Workflow，并通过分阶段生成约束提升输出可控性、稳定性与可复核性。

---

# 2. Project Goal

本项目构建了一套从需求分析到测试设计的 Multi-Agent Workflow。

目标不是构建复杂 Agent 平台，也不是证明“多 Agent 一定优于单 Prompt”。

项目核心目标是：

> 将测试工作中的“需求分析 → 风险识别 → 测试设计 → 汇总复核”流程结构化，并验证在需求信息不完整的情况下，如何通过职责边界、信息来源限制、结构化输出和停止生成机制控制模型输出边界。

---

## Goal 1：测试工作流结构化

将真实测试工作中的前置分析流程拆解为多个可观察、可复核的 Agent 阶段。

---

## Goal 2：降低自动补全倾向

限制模型在需求信息不完整时进行常识补全，避免将未确认信息当作已知事实。

---

## Goal 3：暴露信息缺口

当需求缺少流程、规则、条件、页面、异常处理等信息时，通过 open_questions 显式暴露，而不是由模型默认补齐。

---

## Goal 4：控制风险泛化

限制风险识别只基于原始需求与上游输出，避免生成与当前需求无直接关系的通用 checklist。

---

## Goal 5：支持停止生成

在信息不足时允许系统停止生成完整测试用例，改为输出测试草案和待确认项。

---

## Goal 6：提升结果可复核性

通过结构化输出、中间状态和人工复核入口，让输出结果能够被追踪、复核和归因。

---

# 3. Core Problem

实验过程中重点关注以下问题：

---

## Problem 1：Implicit Completion

模型自动补全原始需求中未出现的信息。

例如：

* 验证码
* 密码
* 邮箱
* 页面按钮
* 输入规则
* 具体错误提示

这类内容可能符合常识，但并不来自需求文本，会掩盖真实信息缺口。

---

## Problem 2：Risk Generalization

模型生成与当前需求无直接关系的通用风险。

例如：

* 泛化权限风险
* 泛化性能风险
* 泛化并发风险
* 默认系统安全风险

这会导致风险识别变成通用 checklist，而不是当前需求的风险分析。

---

## Problem 3：Pseudo-complete Output

模型在信息不足时仍生成完整结果。

例如：

* 完整测试用例
* 详细测试步骤
* 完整验收标准

这类输出表面完整，但建立在未确认信息之上，容易误导后续使用者。

---

## Problem 4：Role Contamination

不同 Agent 逐渐越过职责边界。

例如：

* Agent1 在需求解析阶段补充业务规则
* Agent2 在风险识别阶段引入未出现机制
* Agent3 在测试设计阶段补全测试前提
* Agent4 在汇总阶段新增问题和风险

这会导致错误信息在链路中逐层放大。

---

## Problem 5：Output Instability

复杂需求下输出波动较大。

尤其在多动作需求、流程型需求和 AI 能力型需求中，模型容易出现：

* 动作遗漏
* 问题过度展开
* open_questions 波动
* 风险表达不一致
* 汇总阶段边界漂移

---

# 4. Solution Overview

项目采用串行 Multi-Agent Workflow：

```text
Requirement Text
↓
Agent 1：Requirement Parsing
↓
Agent 2：Risk Analysis
↓
Agent 3：Test Design
↓
Agent 4：Result Summary
↓
Structured Output
```

每个 Agent 对应测试工作流中的一个阶段：

| 测试工作阶段 | Agent                       | 核心职责                                     |
| ------ | --------------------------- | ---------------------------------------- |
| 需求理解   | Agent 1：Requirement Parsing | 抽取需求目标、角色、动作、边界和待澄清问题                    |
| 风险判断   | Agent 2：Risk Analysis       | 基于需求和 open_questions 识别歧义、缺失、异常流和数据/状态风险 |
| 测试设计   | Agent 3：Test Design         | 在已知信息范围内生成测试点、验收标准和测试草案                  |
| 汇总复核   | Agent 4：Result Summary      | 汇总上游结果，输出关键待确认项和人工复核建议                   |

该设计不是为了增加 Agent 数量，而是为了让测试工作流中的不同阶段具备清晰职责，并对每一层施加不同的生成约束。

通过：

* 职责边界
* 信息来源限制
* 输出结构约束
* 中间状态设计
* 停止生成机制
* 人工复核入口

控制模型生成行为。

---

# 5. Design Principles

项目遵循以下设计原则。

---

## Principle 1：Workflow First

Agent 拆分来源于真实测试工作流，而不是为了堆叠 Agent 数量。

真实测试工作需要先完成需求理解、风险判断和异常流程分析，再进入测试设计。

因此，本项目将这些阶段显式拆解为 AI Workflow。

---

## Principle 2：Single Responsibility

单个 Agent 仅负责一个认知任务。

避免在同一次生成中同时承担：

* 信息提取
* 风险判断
* 测试设计
* 结果汇总

等不同职责。

---

## Principle 3：Structured Output

所有 Agent 输出固定结构。

保证结果：

* 可比较
* 可追踪
* 可复核
* 可归因

---

## Principle 4：Explicit Uncertainty

信息不足时，系统必须显式暴露问题，而不是补全答案。

缺失信息应进入：

```text
open_questions
```

而不是被模型转化为默认规则。

---

## Principle 5：Stop Generation

允许系统在信息不足时停止生成完整结果。

尤其在测试设计阶段，应优先输出：

```text
test_case_drafts
```

而不是伪完整的：

```text
test_cases
```

---

## Principle 6：Human Review

保留人工复核节点。

AI 输出不得直接替代需求评审、规则确认和测试用例最终确认。

---

# 6. Scope

当前版本验证：

* 测试工作流 AI 化
* 分阶段 Agent 职责拆分
* 输出可控性
* 信息缺口识别
* 风险泛化控制
* 停止生成机制
* 结构化输出设计
* 多类型 case 下的基本稳定性

---

当前不验证：

* 多模型协同
* 动态路由
* Tool Calling
* 长期记忆
* 自动评估系统
* 企业级 Agent 编排系统
* 产品化平台建设
* 行业知识库
* 完整上下文管理系统

---

# 7. Evaluation Strategy

当前项目不以“单 Prompt 与多 Agent 的性能对比”作为核心验证方式。

项目评估重点是：

> 在测试工作流的不同阶段，模型是否能够遵守生成边界，并在信息不足时暴露缺口而不是补全结果。

---

## 7.1 当前观察维度

重点观察：

* 是否出现自动补全
* 是否正确暴露信息缺口
* 风险是否与当前需求相关
* 是否生成通用 checklist
* 是否在信息不足时生成伪完整测试用例
* 汇总阶段是否新增问题或风险
* 输出结构是否稳定
* 问题来源是否可追踪

---

## 7.2 当前验证方式

当前主要通过：

* 多类型需求 case 运行
* Prompt 收敛记录
* Failure Mode 分析
* 输出版本对比
* 人工复核判断

验证系统的输出边界控制能力。

---

## 7.3 后续评估补充

当前版本仍需要补充：

```text
Expected Behavior Baseline
```

用于为不同需求 case 定义：

* 必须识别的动作
* 必须暴露的信息缺口
* 禁止补全的内容
* 允许进入风险识别的内容
* 信息不足时是否应停止生成完整测试用例
* 汇总阶段是否允许新增问题

该评测集用于判断后续 Prompt 或结构调整是否真正减少了补全、泛化和伪完整生成。

---

# 8. Key Findings

实验过程中发现：

---

## Finding 1：多 Agent 本身并不会自动提升质量

Agent 拆分可以降低单阶段任务复杂度，但无法自动解决：

* 补全
* 泛化
* 扩写
* 伪完整生成

问题。

---

## Finding 2：模型天然倾向补全缺失信息

当需求文本不完整时，模型容易根据常识补充规则、页面、流程和异常处理。

这在测试设计场景中存在风险，因为未确认信息会被下游继续使用。

---

## Finding 3：系统稳定性主要来自约束

系统稳定性主要来自：

* 职责边界
* 信息来源约束
* 输出结构约束
* 停止生成机制
* 人工复核入口

而不是 Agent 数量本身。

---

## Finding 4：中间状态能够提升可观测性

例如 Agent1 的三阶段结构：

```text
Parsing
↓
Gap Detection
↓
Selection
```

能够提升：

* 可观测性
* 可解释性
* 问题定位能力
* 复杂需求下的问题覆盖稳定性

---

## Finding 5：系统需要支持停止生成

系统需要支持：

```text
Information Missing
↓
Expose Open Questions
↓
Stop Complete Generation
```

而不是：

```text
Information Missing
↓
Automatic Completion
↓
Pseudo-complete Output
```

---

## Finding 6：输入上下文限制了准确性上限

当前版本主要基于单段需求文本输入。

因此，它更适合：

* 暴露信息缺口
* 控制错误生成
* 输出测试设计草案

而不适合直接生成高度准确的完整测试用例。

如果后续要提升真实业务场景下的测试设计质量，需要引入：

* 项目背景
* 业务规则
* 页面信息
* 系统上下文
* 行业背景
* 历史缺陷

等 Context Layer。

---

# 9. Project Value

本项目最终沉淀的并不仅仅是一个 Multi-Agent Demo。

更重要的是：

一套将测试工作流迁移为 AI Workflow 的结构化方法，以及一套针对 LLM 输出问题的生成约束思路。

项目验证了：

* 如何将测试工作中的需求分析、风险识别、测试设计和汇总复核拆解为 AI Workflow
* 如何识别模型在不同阶段的失控模式
* 如何限制模型越界推断
* 如何通过职责拆分降低复杂任务难度
* 如何通过结构化输出提升稳定性
* 如何通过中间状态提升可观测性
* 如何在信息不足时停止生成
* 如何保留人工复核节点，避免错误结果直接进入下游流程

---

# 10. Conclusion

本项目最终验证的不是：

```text
多 Agent 一定优于单 Prompt
```

而是：

```text
在需求到测试设计这类多阶段任务中，测试工作流可以被结构化为 AI Workflow，并通过分阶段职责边界和生成约束提升输出可控性。
```

多 Agent 的价值不在于增加 Agent 数量，而在于：

* 承接真实测试工作流中的不同阶段
* 让每一层职责边界更清晰
* 让中间结果可观察
* 让问题来源可定位
* 让下游输入范围可控制
* 让信息不足时可以停止生成

系统稳定性主要来自：

* 职责边界
* 信息来源限制
* 输出结构约束
* 中间状态设计
* 停止生成机制
* 人工复核入口

而非模型能力本身或 Agent 数量本身。
