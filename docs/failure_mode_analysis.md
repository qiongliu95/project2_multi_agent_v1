# Failure Mode Analysis

## 1. Purpose

本文档用于总结项目《Requirement-to-Test Multi-Agent Workflow》在实验过程中出现的典型失败模式（Failure Modes）、根因分析与收敛策略。

本项目不是为了证明“多 Agent 一定优于单 Prompt”，而是将真实测试工作中的：

```text
需求分析
↓
风险识别
↓
测试设计
↓
汇总复核
```

结构化为一套 AI Workflow，并重点观察：

> 在需求信息不完整、边界不明确的情况下，模型在哪些阶段容易失控，以及如何通过分阶段约束提升输出可控性与可复核性。

因此，本文档重点不是分析模型“能不能生成内容”，而是分析：

* 模型为什么会生成错误内容；
* 错误生成发生在哪个阶段；
* 错误如何沿工作流向下游传播；
* 哪些约束策略能够降低错误生成；
* 系统如何在信息不足时停止伪完整输出。

项目重点逐步从：

```text
Generation
```

转向：

```text
Generation Control
```

---

# 2. Why Failure Mode Analysis

在项目早期阶段，系统已经能够完成：

* Requirement Parsing
* Risk Analysis
* Test Design
* Result Summary

但实验过程中发现：

即使工作流能够正常运行，系统仍会出现：

* 自动补全
* 风险泛化
* 职责越界
* 伪完整结果
* 汇总扩写
* 输出波动

这些问题并非简单增加 Prompt 规则就能完全解决。

因为在需求到测试设计场景中，LLM 天然倾向于把不完整需求补成完整流程，把未确认信息转化为默认规则，并继续基于这些假设生成风险、测试点和验收标准。

这会导致：

```text
需求信息不足
↓
模型自动补全
↓
风险识别承接补全信息
↓
测试设计生成伪完整用例
↓
汇总阶段进一步固化错误
```

因此，Failure Mode Analysis 的目的不是单纯记录错误，而是用于识别：

* 问题是什么；
* 问题出现在哪个 Agent；
* 问题为什么发生；
* 问题会如何影响下游；
* 应该通过 Prompt、Schema、Architecture 或 Process 哪一层收敛。

---

# 3. Failure Modes

---

## Failure Mode 1：Implicit Completion

### Symptoms

模型会自动补充需求中未出现的信息。

例如，原始需求为：

> 用户可以通过手机号注册账号，注册后可以登录系统。

模型可能进一步生成：

* 验证码机制
* 密码规则
* 邮箱绑定
* 登录失败处理
* 页面输入框
* 错误提示文案

这些内容并未出现在原始需求中。

---

### Root Cause

模型倾向构造完整业务流程。

当需求信息不足时，模型会利用训练阶段积累的常见业务模式进行补全。

在需求分析场景中，这种能力表面上会让结果更完整，但实际上会把“未确认信息”伪装成“已知事实”。

---

### Impact

该问题会造成：

* 掩盖真实信息缺口；
* 污染后续 Agent 输入；
* 降低输出可信度；
* 难以区分事实与推断；
* 让测试设计建立在未确认规则之上。

例如，一旦 Agent1 补充了“验证码”，Agent2 可能继续生成验证码风险，Agent3 可能继续设计验证码测试点，最终导致整条链路围绕一个原需求中不存在的机制展开。

---

### Convergence Strategy

对 Agent1 施加信息来源约束：

Agent1 仅允许基于：

```text
requirement_text
```

进行信息提取。

禁止：

* 常识补全；
* 默认规则推断；
* 未出现机制扩展；
* 具体页面或输入规则补充。

对于缺失信息，统一进入：

```text
open_questions
```

而不是由模型自行补齐。

---

### Result

Agent1 从：

```text
生成型需求解析
```

转变为：

```text
提取型需求解析
```

系统开始显式暴露信息缺失，减少需求解析阶段对下游的污染。

---

## Failure Mode 2：Risk Generalization

### Symptoms

Agent2 倾向生成通用风险清单。

例如，需求为：

> 用户可以创建和删除自己的笔记。

模型可能生成：

* 权限风险
* 并发风险
* 性能风险
* 数据安全风险
* 操作审计风险

即使这些内容在当前需求中并未体现。

---

### Root Cause

模型倾向套用通用风险模板。

在测试经验中，权限、并发、性能、数据一致性确实都是常见风险，但并不是所有需求都需要在当前阶段展开这些风险。

如果没有限制风险来源，Agent2 会从“当前需求风险识别”滑向“通用测试 checklist 生成”。

---

### Impact

该问题会造成：

* 风险失焦；
* 输出价值下降；
* 当前需求的真实问题被泛化列表淹没；
* Agent3 被引导生成更多与当前需求弱相关的测试点；
* 系统从需求分析工具变成通用风险枚举器。

---

### Convergence Strategy

限制 Agent2 的风险来源。

Agent2 仅允许引用：

* requirement_text
* Agent1 输出
* open_questions

禁止引入：

* 默认系统能力；
* 通用 checklist 风险；
* 原需求未出现的具体实现机制；
* 与当前需求没有直接关系的风险项。

风险表达应保持与当前需求相关。

---

### Result

Agent2 从：

```text
风险生成
```

转变为：

```text
风险识别
```

风险开始围绕当前需求和已暴露的信息缺口展开，减少泛化扩张。

---

## Failure Mode 3：Pseudo-complete Testing

### Symptoms

在需求明显不完整时，Agent3 仍然生成：

* 完整测试用例；
* 详细测试步骤；
* 完整验收标准；
* 前置条件；
* 预期结果。

输出结果看起来完整，但建立在大量未确认信息之上。

---

### Root Cause

模型倾向完成任务。

当任务被描述为“生成测试用例”时，模型会倾向于交付一个完整结果，即使输入信息不足。

这会导致模型把需求缺失部分自动补全，再基于补全内容生成测试步骤。

---

### Impact

该问题会造成：

* 掩盖需求缺失；
* 输出具有误导性；
* 测试草案被误认为可执行用例；
* 错误被进一步固化；
* 人工复核压力后移。

在真实研发协作中，伪完整输出比“不输出完整结果”更危险，因为它会让使用者误以为需求已经具备测试设计条件。

---

### Convergence Strategy

调整 Agent3 输出结构。

将：

```text
test_cases
```

替换为：

```text
test_case_drafts
```

并引入停止生成机制。

当信息不足时：

* 不生成完整测试用例；
* 不补全业务规则；
* 只保留测试方向；
* 输出测试草案；
* 保留待确认项。

---

### Result

Agent3 从：

```text
完整生成导向
```

转变为：

```text
约束输出导向
```

系统开始保留不确定性，并避免在信息不足时生成伪完整测试结果。

---

## Failure Mode 4：Role Contamination

### Symptoms

不同 Agent 开始越过自身职责边界。

例如：

Agent1 在需求解析阶段：

* 扩展流程；
* 推断规则；
* 补充页面机制。

Agent2 在风险识别阶段：

* 推断系统能力；
* 新增风险维度；
* 扩展当前需求未出现的规则。

Agent3 在测试设计阶段：

* 补全测试前提；
* 生成完整测试步骤；
* 引入未确认预期结果。

Agent4 在汇总阶段：

* 新增问题；
* 新增风险；
* 扩展总结内容；
* 将抽象风险具体化。

---

### Root Cause

职责边界不明确。

LLM 倾向于完成整体任务，而不是严格停留在某个局部职责中。

如果 Agent 的输入范围、输出字段和禁止行为没有明确限制，每个 Agent 都可能重新解释整个需求，从而产生职责污染。

---

### Impact

该问题会造成：

* 问题逐层放大；
* 结果不可追踪；
* 无法判断错误来自哪个阶段；
* Agent 拆分价值下降；
* 下游输出被上游越界内容污染。

如果所有 Agent 都在重新完成完整任务，那么多阶段工作流就会退化为多次重复生成。

---

### Convergence Strategy

强化职责边界。

Agent1：

```text
仅负责需求信息提取与信息缺口暴露
```

Agent2：

```text
仅负责基于需求与 open_questions 的风险识别
```

Agent3：

```text
仅负责在已知信息范围内进行测试设计
```

Agent4：

```text
仅负责汇总上游已有结果
```

同时通过固定输出 Schema 限制引用范围。

例如：

* Agent2 只能使用 requirement_text 与 Agent1 输出；
* Agent3 只能基于已知信息与风险项输出测试草案；
* Agent4 只能复用上游结果，不得新增问题。

---

### Result

系统开始具备：

* 可解释性；
* 可追踪性；
* 可定位性；
* 下游污染控制能力。

Agent 拆分开始真正服务于测试工作流治理，而不是单纯增加生成步骤。

---

## Failure Mode 5：Single-stage Parsing Instability

### Symptoms

复杂需求下，Agent1 单阶段解析容易出现：

* 动作遗漏；
* open_questions 波动；
* 提问结果不稳定；
* 多动作覆盖不完整；
* 需求提取与问题生成互相干扰。

例如，在并列动作需求中：

> 用户可以创建和删除自己的笔记。

模型可能只关注“创建”，遗漏“删除”，或在 open_questions 中生成过度细化的问题。

---

### Root Cause

单阶段 Agent 同时承担多个任务：

* 信息提取；
* 缺失识别；
* 问题决策。

这三个任务在复杂需求下会互相干扰。

尤其当 Agent 需要同时判断“需求里有什么”和“缺什么”时，模型容易在提取与推断之间摇摆。

---

### Impact

该问题会造成：

* 复杂需求稳定性下降；
* 问题覆盖率波动；
* 输出一致性不足；
* 下游风险识别和测试设计受到影响。

如果 Agent1 的结构基础不稳定，后续 Agent 即使有约束，也会基于不稳定输入继续生成。

---

### Convergence Strategy

Agent1 从单阶段升级为三阶段结构：

```text
Parsing
↓
Gap Detection
↓
Selection
```

并新增：

```text
action_gap_candidates
```

作为中间状态。

其中：

* Parsing：识别需求中的角色、动作、对象和已知信息；
* Gap Detection：针对每个动作识别信息缺口；
* Selection：判断哪些缺口需要进入 open_questions。

---

### Result

复杂需求下：

* 多动作覆盖更稳定；
* open_questions 波动减少；
* 问题来源更可追踪；
* 提取与提问之间的干扰降低。

---

## Failure Mode 6：Summary Drift

### Symptoms

Agent4 在汇总阶段可能出现扩写倾向。

具体表现为：

* 新增 open_questions；
* 新增风险；
* 将抽象风险具体化；
* 将参考信息包装成关键问题；
* 对上游结果进行过度解释。

例如，Agent1 只提出“异常处理规则需要明确”，Agent4 可能扩展为“输入为空、超长、非法字符等异常处理需要明确”。

---

### Root Cause

汇总任务本身容易诱导模型进行语言润色、扩展和归纳。

如果没有明确限制，模型会认为“总结”需要更完整、更清晰，从而主动补充细节。

---

### Impact

该问题会造成：

* 前面已经收敛的边界被重新放大；
* 最终结果包含上游未确认信息；
* 关键待确认项失去可追溯性；
* 用户误以为新增问题来自前面分析结果。

---

### Convergence Strategy

限制 Agent4 的汇总范围。

Agent4 只能复用：

* Agent1 open_questions；
* Agent2 已识别风险；
* Agent3 已输出测试草案；
* 上游明确存在的信息。

禁止：

* 新增问题；
* 新增风险；
* 扩展具体异常类型；
* 引入新的业务假设。

---

### Result

Agent4 从：

```text
扩写型总结
```

转变为：

```text
受控汇总
```

最终输出更可追溯，也更符合人工复核场景。

---

# 4. Key Findings

通过多个阶段实验，项目得到以下结论。

---

## Finding 1：模型天然倾向补全缺失信息

如果没有信息来源限制，模型会持续扩展未确认内容。

在需求到测试设计场景中，这会导致后续风险识别和测试设计建立在假设之上。

---

## Finding 2：多 Agent 本身并不会自动提升稳定性

Agent 拆分可以降低单阶段任务复杂度，但缺少边界约束时，系统仍会出现：

* 自动补全；
* 风险泛化；
* 伪完整结果；
* 汇总扩写。

因此，Agent 数量不是稳定性的根本来源。

---

## Finding 3：稳定性主要来自生成约束

系统稳定性主要来自：

* 职责边界；
* 信息来源限制；
* 输出结构约束；
* 停止生成机制；
* 人工复核入口。

---

## Finding 4：中间状态能够提升可观测性

例如 Agent1 的：

```text
Parsing
↓
Gap Detection
↓
Selection
```

能够让系统看到：

* 原需求中有哪些动作；
* 每个动作缺少哪些信息；
* 哪些缺口最终进入 open_questions。

中间状态的价值在于提升可观测性、可解释性和问题定位能力。

---

## Finding 5：系统需要支持停止生成

系统需要支持：

```text
Information Missing
↓
Expose Open Questions
↓
Stop Complete Generation
```

而不是：

```text
Information Missing
↓
Automatic Completion
↓
Pseudo-complete Output
```

在测试设计场景中，错误完整结果比不完整草案更危险。

---

## Finding 6：测试工作流拆分本身需要配合约束

本项目中的 Agent 拆分来源于真实测试工作流：

```text
需求分析
↓
风险识别
↓
测试设计
↓
汇总复核
```

但流程拆分只是基础结构。

只有配合每一层的生成约束，才能让系统输出更加可控。

---

# 5. Conclusion

本项目最终验证：

AI Workflow 的主要挑战并非生成能力不足，而是生成失控。

在需求到测试设计场景中，LLM 很容易在信息不足时自动补全，在风险识别阶段泛化扩展，在测试设计阶段生成伪完整结果，并在汇总阶段重新扩大边界。

因此，系统稳定性主要来自：

* 明确职责边界；
* 信息来源限制；
* 输出结构约束；
* 中间状态设计；
* 停止生成机制；
* 人工复核策略。

多 Agent 的价值不在于增加 Agent 数量，而在于承接真实测试工作流中的不同阶段，并通过结构化约束提升输出质量与可控性。

当前版本更适合作为：

* 测试工作流 AI 化原型；
* 生成约束机制验证 Demo；
* 测试经验迁移到 AI 产品设计的展示项目。

后续如果要进一步提升真实业务场景下的测试设计准确性，需要补充：

* Expected Behavior Baseline；
* 项目背景；
* 业务规则；
* 页面信息；
* 系统上下文；
* 行业背景。

其中，Expected Behavior Baseline 用于解决“如何判断改动是否有效”的问题；Context Layer 用于解决“如何提高真实业务准确性”的问题。
