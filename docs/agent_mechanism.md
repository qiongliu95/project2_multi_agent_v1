# Agent Mechanism Design

## 1. 文档目标

本文档用于说明项目二《需求到测试设计的 Multi-Agent Workflow》中各项机制设计的原因与目的。

本项目重点不是构建复杂 Agent 平台。

而是：

验证：

- 多 Agent 拆分是否能够提升输出可控性
- 是否能够降低模型自动补全倾向
- 是否能够提升结构稳定性
- 是否能够让信息缺失显式暴露
- 是否能够在信息不足时停止生成

因此：

本项目更关注：

- Agent 职责边界
- 信息流控制
- 输出结构约束
- 中间状态设计
- 人工复核机制

而不是：

- 模型能力堆叠
- 多模型协同
- 工具调用编排
- 自动化系统扩张

---

# 2. 为什么需要 Multi-Agent

在项目初期，曾尝试由单阶段生成直接完成：

- 需求解析
- 风险识别
- 测试设计
- 结果汇总

但在实验过程中发现：

单阶段生成容易出现：

- 常识补全
- 风险泛化
- 测试扩写
- 输出结构波动
- 信息来源混乱

进一步分析后发现：

单阶段任务实际上同时包含：

- 信息提取
- 问题识别
- 风险判断
- 测试设计
- 汇总表达

多个不同目标。

这些任务混合在同一次生成中时：

容易导致：

- 推理链过长
- 输出职责混杂
- 下游无法定位问题来源

因此：

项目后续采用：

```text
需求解析
→ 风险识别
→ 测试设计
→ 结果汇总
````

的串行 Multi-Agent 结构。

用于：

* 拆分复杂任务
* 限制单 Agent 职责
* 提升结构稳定性
* 降低不同任务之间的相互干扰

---

# 3. 为什么采用串行结构

项目当前采用：

```text
Agent 1 → Agent 2 → Agent 3 → Agent 4
```

的固定串行流程。

原因包括：

---

## 3.1 降低系统复杂度

当前项目重点是：

验证：

* Agent 拆分是否有效
* 输出是否稳定

因此：

优先采用：

* 固定流程
* 固定顺序
* 固定职责

而不是：

* 动态路由
* 条件分支
* 多 Agent 调度

---

## 3.2 提升问题可定位性

串行结构下：

每个 Agent 都有：

* 固定输入
* 固定输出
* 固定职责

因此：

更容易定位：

问题究竟出现在哪个阶段。

例如：

* 信息补全来自 Agent 1
* 风险扩写来自 Agent 2
* 伪完整测试来自 Agent 3

---

## 3.3 便于实验对比

串行结构更适合：

* 单 Agent vs 多 Agent 对照
* Prompt 收敛实验
* 输出结构分析

因此：

更适合作为第一阶段验证方案。

---

# 4. 为什么采用结构化输出

项目所有 Agent 均采用：

JSON 风格结构化输出。

例如：

```json
{
  "main_flow": [],
  "open_questions": [],
  "core_test_points": []
}
```

采用结构化输出的原因不是：

“格式统一”。

而是：

---

## 4.1 提升可复核性

结构化字段可以明确区分：

* 主流程
* 风险
* 测试点
* 待确认问题

避免：

所有内容混合在自然语言中。

---

## 4.2 提升可定位性

当输出异常时：

可以快速定位：

究竟是哪个字段出现问题。

例如：

* open_questions 扩写
* ambiguity_risks 泛化
* acceptance_criteria 越界

---

## 4.3 提升可比较性

结构化输出更适合：

* 多轮实验对比
* baseline 对照
* case 分析

---

## 4.4 降低下游污染

固定字段能够限制：

不同 Agent 之间的信息扩散。

避免：

后续 Agent 自由改写前置结果。

---

# 5. 为什么限制信息来源

项目在实验过程中发现：

模型在需求信息不足时：

会自动补全：

* 默认业务规则
* 常见交互方式
* 通用系统能力

例如：

* 验证码
* 密码规则
* 页面流程
* 权限机制

这些内容并未在原需求中明确出现。

因此：

项目后续明确限制：

Agent 输出只能基于：

* requirement_text
* 上游 Agent 输出

禁止：

* 默认业务补全
* 未出现规则推断
* 常识扩展

---

## 当前目标

限制信息来源的核心目的不是：

“减少输出内容”。

而是：

* 保持输出可追溯
* 暴露真实信息缺失
* 降低错误前提扩散

---

# 6. 为什么引入 open_questions

在实验初期：

模型在信息不足时：

倾向继续生成完整结果。

导致：

* 隐式补全
* 默认规则生成
* 伪完整测试

因此：

项目后续引入：

```json
open_questions
```

用于：

显式记录当前需求中的缺失信息。

---

## open_questions 的作用

---

### 6.1 暴露不确定性

当信息不足时：

系统不再继续补全。

而是：

直接暴露：

“当前仍缺少哪些信息”。

---

### 6.2 降低错误扩散

缺失信息不会继续被：

* 风险识别
* 测试设计
* 汇总阶段

误认为：

“已经确认”。

---

### 6.3 支持人工复核

open_questions 可以作为：

人工澄清入口。

用于：

* 需求补充
* 规则确认
* 流程确认

---

# 7. 为什么支持停止生成

项目在 Agent 3 阶段发现：

即使需求明显不完整，

模型仍会继续生成：

* 完整测试用例
* 验收标准
* 测试步骤

导致：

输出看起来完整。

但：

实际上建立在大量未确认信息上。

因此：

项目后续明确支持：

“停止生成”。

---

## 当前机制

当缺少关键信息时：

允许：

* 不生成完整测试用例
* 仅输出测试方向
* 输出待确认问题

并将：

```json
test_cases
```

调整为：

```json
test_case_drafts
```

用于明确：

当前结果并非最终完整测试方案。

---

## 当前目标

支持停止生成的目的不是：

“减少生成能力”。

而是：

避免：

系统在信息不足时继续伪造完整结果。

---

# 8. 为什么 Agent 1 从单阶段升级为三阶段

这是项目后期最重要的结构调整之一。

---

## 8.1 单阶段 Agent 1 的问题

初期：

Agent 1 同时负责：

* 信息提取
* 缺失识别
* 问题生成

在复杂需求下容易出现：

* 动作遗漏
* 问题波动
* open_questions 不稳定

进一步分析后发现：

多个任务同时进行时：

不同目标之间会互相干扰。

---

## 8.2 从单阶段升级为三阶段

项目后续将 Agent 1 调整为：

```text
Parsing
→ Gap Detection
→ Selection
```

分别负责：

| 阶段            | 职责       |
| ------------- | -------- |
| Parsing       | 提取结构信息   |
| Gap Detection | 识别信息缺口   |
| Selection     | 决定保留哪些问题 |

---

## 8.3 为什么需要中间态

在三阶段结构中：

新增：

```text
action_gap_candidates
```

作为中间状态。

原因包括：

---

### 提升可观测性

能够明确看到：

每个动作缺少哪些信息。

---

### 分离识别与决策

区分：

* “发现问题”
  和
* “保留问题”

避免：

多个任务互相干扰。

---

### 提升稳定性

在复杂需求下：

能够降低：

* 问题随机波动
* 动作遗漏
* 提问不一致

---

## 8.4 当前效果

在当前实验中：

三阶段结构相比单阶段：

表现出：

* 更稳定的问题覆盖
* 更稳定的 open_questions
* 更强的问题可追踪性

---

# 9. 为什么保留人工复核

项目在实验过程中发现：

即使经过：

* Agent 拆分
* Prompt 约束
* 输出结构限制

系统仍可能出现：

* 语义扩展
* 信息误解
* 输出偏移

因此：

项目没有将系统定位为：

“完全自动决策系统”。

而是：

保留：

```json
human_review_required
```

用于：

人工确认关键输出。

---

## 当前目标

人工复核的作用包括：

* 防止错误结果直接进入下游流程
* 保留需求确认能力
* 保留业务决策能力
* 降低错误自动化风险

---

# 10. 当前机制边界

当前项目重点关注：

* Agent 拆分是否有效
* 输出是否稳定
* 信息缺失是否能够被正确暴露
* 输出是否具备可复核性

当前不关注：

* 多模型协同
* 动态路由
* 工具调用
* 自动化执行
* 产品化平台能力

因此：

当前机制重点属于：

AI Workflow 中的：

* 输出约束
* 结构稳定性
* 质量控制

而不是：

复杂 Agent 平台工程。

---

# 11. 当前项目结论

通过当前实验，项目观察到：

---

## 结论 1

多 Agent 拆分本身并不会自动提升系统稳定性。

系统稳定性更依赖：

* 职责边界
* 信息来源限制
* 输出结构约束
* 中间状态设计

---

## 结论 2

复杂任务拆分后：

系统在当前实验范围内：

表现出：

* 更稳定的结构输出
* 更好的问题可定位性
* 更低的信息扩散风险

---

## 结论 3

当前项目重点不是：

“生成更多内容”。

而是：

* 如何限制错误生成
* 如何暴露信息缺失
* 如何降低结构失控
* 如何保留人工复核能力

---

## 结论 4

项目最终验证的重点是：

AI Workflow 中：

* 输出约束
* 结构控制
* 中间状态设计
* 质量控制

等问题。
